Bob 大叔手把手教你写出“人能看懂”的代码：命名、函数、注释、格式，条条都是血泪经验。

总体观点

2008 年，罗伯特·马丁开场很狠：代码永远不会消失，需求永远在变，“写出整洁的代码”是程序员的本职工作，不是锦上添花。这本书是他几十年经验浓缩的“代码卫生手册”。

核心观点：代码是写给人看的，顺便让机器执行。读代码的时间是写代码的十倍以上，所以第一要务是“好读”。名字名副其实、函数短到只做一件事、注释能不写就不写、格式像报纸一样有条理。

它把“代码品味”这种玄学变成可执行、可检查的清单。和《重构》常被一起读：一个教你“怎么写出好代码”，一个教你“怎么把坏代码变好”。

核心观点

  1. 1. 名字要名副其实

    好名字让读者不看实现就知道它是干嘛的；烂名字（data、temp、info）等于埋地雷。宁可长一点，也别含糊。

    getData() 取什么数据？改成 getUserOrderHistory() 三秒看懂。布尔 flag 改成 isOrderPaid，一眼知道“订单是否已支付”。

  2. 2. 函数只做一件事，而且要做好

    函数要小到只做一件事：能用一句话说清它在干嘛、且这句话里没有“和”“或”，就是一件事。函数一长，读的人脑子里记一堆上下文，累且容易错。

    processOrder() 200 行又校验库存又算价格又发短信：拆成 checkStock()、calculatePrice()、sendSms()、saveOrder()，主函数变四行“目录”，想看细节再点进去。

  3. 3. 注释是失败，别用注释弥补烂代码

    好代码不需要注释解释“在做什么”，代码自己说清楚了。需要写注释，往往说明代码没写好。但解释“为什么”这么写的注释还是必要的——那是代码说不出来的。

    “i 加 1”是废话注释；“订单 30 分钟未支付自动取消，法务定的规则”有用——它解释的是代码背后的“为什么”。

  4. 4. 童子军规则：让营地比你来时更干净

    离开营地要比来时更干净。每次改代码顺手让它干净一点点：改个烂命名、删段重复、拆个长函数。不用多，每次一点点，质量像复利一样越滚越好。

    修 bug 看到拼错的 recieve，顺手改成 receive 再提交。一年下来，无数个小动作让代码库慢慢变干净。

  5. 5. 别返回null，用异常说清楚

    返回 null 是最常见的偷懒：调用方一不留神忘了判空，线上就崩。要么返回有意义的东西（空集合），要么直接抛异常——异常藏不住，不处理立刻告诉你。

    查用户订单，用户没订单返回 null，调用方写 order.getTotal() 直接空指针，线上事故。返回空列表，循环一下啥事没有。

  6. 6. 测试是最好的文档

    一套好的单元测试，比任何文档都更能说明“代码是干嘛的”——文档会过时，测试不会，因为测试不过，代码合并不进去。

    新同事想知道下单接口有哪些规则，翻三个月没更新的 Wiki，不如直接看测试：满 200 减 20、未支付 30 分钟自动取消……条条测试就是条条活规矩。

  7. 7. 一个类只有一个“变”的理由

    一个类只干一件事，只因为一种原因被修改。又管数据库又管发邮件又管算价格，需求一变就得改，改多就容易出 bug。职责分开，各自安好。

    UserService 里有注册、发欢迎邮件、生成报表，改邮件模板一不小心碰坏注册逻辑。拆成三个类，改邮件只动 EmailService，注册稳如泰山。

▼ 一、整洁代码哲学与工匠职业素养 代码质量是专业程序员不可妥协的自尊防线

读写时间比与破窗理论

阅读代码的时间远超编写代码的时间

  • • 读写比高达 10:1：工程师大部分时间在翻看既有代码理清上下文，让读代码变轻松就是在成倍提高整体生产力
  • • 糟糕代码的恶性循环：为了赶进度凑合写脏代码 → 架构逐渐腐化 → 之后每次修改都加剧破损 → 最终系统彻底无法维护
  • • 童子军军规（The Boy Scout Rule）：离开营地时，让它比你发现它时更干净；每次提交都顺手改好一个变量名或拆掉一个小函数

专业主义与质量底线

工程师必须对自己的产出承担不可推卸的责任

  • • ‘唯有快跑，方能持久’：慢工出细活是伪命题，写混乱的代码不仅当时不快，更会让后续每一步都寸步难行
  • • 对非技术管理者保持专业原则：当医生被病人要求‘别洗手直接手术以赶时间’时医生会拒绝；同理，工程师不能为了虚幻的死线妥协整洁代码底线
▼ 二、命名与排版格式准则 用清晰的符号赋予代码纯粹的可读性

有意义的命名法则

命名是表达意图的第一道关卡

  • • 名副其实（Intention-Revealing）：好名字能直接回答它为什么存在、做什么事、怎么使用，无需注释补充
  • • 避免误导（Avoid Disinformation）：不要用 hp、aix 等专有缩写命名普通变量；非列表不要以 List 结尾
  • • 做有意义的区分：杜绝 ProductInfo 与 ProductData 这种废话同义反复
  • • 可搜索、读得出来的名称：类名应是名词或名词短语（Customer、Account），方法名应是动词或动词短语（postPayment、deletePage）

垂直与水平格式规范

报纸般的排版结构带来极度舒适的扫读体验

  • • 报纸隐喻：代码应该像读《纽约时报》一样，头条在顶部，越往下细节越深，大纲与细节点次分明
  • • 垂直距离与相关性：关系紧密的方法应该在垂直位置上紧挨着，调用者应该放在被调用者的上方
  • • 控制垂直行数：通常 200 到 500 行的源文件足以承载一个结构完整的模块
▼ 三、精炼函数设计法则 函数的第一规则是短小，第二规则是还要短小

单一职责与抽象层次

函数应该做一件事，做好这件事，且只做这一件事

  • • 单一抽象层次原则（SLAP）：一个函数内的所有语句必须处在同一层抽象级别上，不要将高阶业务判断与底层拼接混在一起
  • • 自顶向下读代码（向下规则）：每个函数后面都跟着下一抽象层次的实现函数，读起来如同自顶向下的诗歌
  • • 消除 Switch 语句：将 switch 隐藏在抽象工厂底层，用多态对象向业务层提供统一契约

函数参数与副作用规避

参数越少越好，消除隐蔽的副作用

  • • 参数数量阶梯：零参数最理想，一元参数次之，二元参数需有充分理由，三元参数必须极力避免，四元以上坚决封装为对象
  • • 无副作用（No Side Effects）：函数绝不能在暗地里偷偷篡改入参或修改隐藏的全局状态
  • • 指令与询问分离（Command Query Separation）：函数要么执行某项操作，要么返回某个查询值，二者不可兼得
▼ 四、注释与错误处理哲学 注释是对不良代码的补偿，错误处理不能打乱核心逻辑

对待注释的清醒态度

用自解释的代码消灭大部分无聊冗余的注释

  • • 注释往往在代码演化中沦为谎言：代码重构了，注释却常常被遗漏更新，极具误导性
  • • 坏注释典型：自怨自艾注释、废话注释、归属签名、被注释掉的代码（直接删，有版本控制）
  • • 好注释场景：法律法规版权声明、对复杂正则的意图阐释、警示潜在严重后果（警告其他开发者勿碰）

优雅的错误处理

将错误处理独立成清晰防线

  • • 使用异常（Exceptions）替代返回错误码：返回错误码会迫使调用方充斥大量的防御式分支，污染主干业务流
  • • 给出异常发生的完整上下文：提供包含操作类型、失败原因的错误消息与日志追踪堆栈
  • • 别返回 Null 值，别传递 Null 值：使用空对象模式（Special Case Object）或 Optional 包装，消灭 NullPointerException
▼ 五、单元测试与类设计（SOLID） 用测试保护演进，用高内聚低耦合构建系统

单元测试五准则（F.I.R.S.T.）

专业敏捷开发不可或缺的测试军规

  • • Fast（快速）：测试必须能毫秒级运行，否则开发者会放弃频繁运行它
  • • Independent（独立）：每个测试之间绝对不可产生状态依赖，必须能以任意顺序执行
  • • Repeatable（可重复）：在任何环境（本地、CI、无网络环境）下都能稳定重复通过
  • • Self-Validating（自足验证）：测试必须有清晰的布尔值通过/失败结果，无需人工看日志判断
  • • Timely（及时）：在编写产品代码之前或同时编写测试，保持测试驱动的敏捷节律

类的高内聚与单一职责

小类优于大类，高内聚隔离外界变化

  • • 类的第一规则是短小：通过职责数量（而非行数）来度量，单一职责原则（SRP）是核心
  • • 内聚性（Cohesion）：类中的方法应积极操作该类的实例变量，内聚度高的类职责清晰
  • • 隔离外部系统与依赖倒置：为第三方库编写包装防腐层，保护核心业务领域不被外部依赖入侵

全书结构

  1. 第1章 整洁代码

    糟糕代码拖垮研发效率直至团队停摆；推行童子军军规——离开时让代码比你来时更干净整洁。

    每次修改遗留代码顺手把周边的变量命名优化并删除废弃注释，一年下来老模块不但没腐化反而越来越清爽。

  2. 第2章 有意义的命名

    命名要名副其实、表达明确意图、避免误导、做有意义的区分并使用读得出来的名称。

    用 `daysSinceLastModification` 替代神秘的 `d` 或 `ds`，任何同事看到代码瞬间明白其含义。

  3. 第3章 函数

    函数应该短小、只做一件事、同一抽象层级，参数尽可能少（最好不超过两个），杜绝输出参数与标识参数。

    将一个带有 `isVip` 标识布尔参数的庞大函数，拆分为 `renderVipPage()` 和 `renderRegularPage()` 两个干净函数。

  4. 第4章 注释

    注释不能美化糟糕的代码，能自表达的代码胜过冗余解释；只在表达意图或警示暗礁时保留必要注释。

    与其在混乱代码旁写三行“这里检查手机号格式”，不如直接提取出一个函数 `isValidPhoneNumber()`。

  5. 第5章 格式

    垂直空白区分逻辑概念段落，横向缩进反映层级结构，代码组织应像报纸新闻一样自上而下顺畅展开。

    把公共入口函数放在类顶端，底层被调用的私有辅助方法放在下方，自上而下阅读如读故事。

  6. 第6章 对象和数据结构

    对象隐藏内部数据并暴露抽象行为，数据结构暴露数据无内在行为，严格遵守得墨忒耳律（只与直接朋友通信）。

    避免写出 `order.getCustomer().getAddress().getCity()` 这样暴露内部深层结构的火车车厢式链式调用。

  7. 第7章 错误处理

    优先使用不可控异常而非返回繁琐错误码，先写 try-catch-finally 建立防线，杜绝传递 null 和返回 null。

    在查询不到数据时返回空的不可变列表 `Collections.emptyList()`，彻底根除调用方到处写 `if (list != null)`。

  8. 第8章 边界

    严密封装第三方库与外部接口调用，编写学习性测试验证外部边界行为，使用适配器隔离不可控依赖。

    引入第三方日志或缓存库时用一个简单的门面包装起来，未来更换开源依赖库只需改动门面类。

  9. 第9章 单元测试

    测试代码与生产代码同等重要，遵循 TDD 与 FIRST 原则（快速、独立、可重复、自我验证、及时）。

    保证几百个单元测试在三秒内跑完且不依赖外部数据库，工程师每次保存代码都能实时验证逻辑正确性。

  10. 第10章 类

    类应该短小并遵循单一职责原则（SRP），追求高内聚，类结构设计应向抽象接口依赖而非具体实现。

    将一个兼顾 SQL 拼装、结果集映射与业务校验的巨型 DAO 类拆分为 SqlBuilder、RowMapper 和 OrderService。

  11. 第11章 系统

    将系统的构造（实例化与装配）与使用分离，使用依赖注入和面向切面（AOP）保持业务逻辑纯粹。

    通过 Spring 依赖注入把数据源注入到业务类中，业务类内部无需出现任何 `new DatabaseConnection()` 硬编码。

  12. 第12章 迭进

    遵循简单设计的四条规则：运行所有测试、消除重复、表达程序员意图、尽量减少类和方法数量。

    在重构复杂逻辑时，先跑通全套自动化测试，再合并两处几乎完全一样的分支计算逻辑，消除冗余。

  13. 第13章 并发编程

    分离并发控制代码与纯业务计算，严格限制共享可变数据的作用域，警惕死锁与线程饥饿。

    使用线程安全的 ConcurrentHashMap 并配合不可变对象传参，避免在普通 HashMap 上手工写多重 synchronized 乱锁。

  14. 第14章 逐步改进

    以 Args 命令行解析器为例，逐步拆解重构，展示从初版杂乱代码演进为优雅面向对象架构的完整实战。

    从一个布尔解析开始，逐步引入泛型参数类型解析器接口，每加一个新类型都保持结构整洁且测试全绿。

  15. 第15章 JUnit内幕

    深入剖析 JUnit 核心模块 ComparisonCompactor，现场演示对已经很优秀的代码进行极限打磨的工匠手艺。

    将变量名反复打磨、拆分带有副作用的布尔提取条件，让原本晦涩的字符串差异对比算法一目了然。

  16. 第16章 重构SerialDate

    解构与重构开源日期库 SerialDate，展示真实工业级遗留代码的完整测试补全、结构梳理与坏味道清洗。

    为没有任何保护的开源老代码补充完整单测，然后清除常量接口反模式，将魔数全部提升为枚举类。

  17. 第17章 味道与启发

    系统汇总涵盖注释、环境、函数、通用设计、命名与测试等维度的坏味道与启发式规则清单，作为代码审查指南。

    在团队 Code Review 中对照清单排查“是否传递了布尔标识”、“是否有重复代码”，快速提升整体代码素养。
