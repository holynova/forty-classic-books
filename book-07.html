总体观点

1994 年，四位博士（人称 GoF）总结 23 种设计模式。在此之前，高手的“套路”只可意会不可言传；这本书起了名字、画了图、写成标准，全世界程序员有了共同的设计语言。

核心观点：很多问题反复出现，就有被验证过的优雅解法——这就是“模式”。模式不是代码，是“解决问题的思路模板”。最大好处不只是写代码，更是沟通：说“这里用观察者模式”，同事立刻懂。

它开创了一个领域：面试必问的单例、工厂、观察者、策略全从这里出来。三十年语言换几代，模式还在用——因为它们针对的是“变化”本身。但作者也提醒：别为用模式而用模式。

核心观点

  1. 1. 针对接口编程，不针对实现编程

    代码依赖“抽象”（接口长什么样），不依赖“具体”（它到底是谁）。接口是契约，实现是干活的人——换人不用换契约，具体实现随便换，调用方不用改。

    代码里到处直接创建 MySQL 存储对象，换 MongoDB 得改几十处。依赖统一存储接口，换时只写个新实现类，调用方一行不动。

  2. 2. 优先用组合，而不是继承

    新手最爱用继承：“狗继承动物，警犬继承狗”，结果改爷爷类孙子类全受影响。能用“组合”（对象里装着另一个对象）解决的别用继承——组合更灵活，想换就换，不用动祖宗。

    鸭子游戏：绿头鸭继承鸭子，后来加“橡皮鸭”不会飞，继承来的飞行方法成 bug。改成组合：想飞装会飞的行为，不想飞装不会飞的，随时换。

  3. 3. 模式是套路，不是银弹

    模式是“特定场景下被验证过的解法”，不是“用了就高级”的勋章。最简单的方案往往最好，为炫技硬套模式只会把代码搞复杂。判断标准：不套模式，这段代码是不是真难受？

    全项目只有一个地方创建对象，非要上“抽象工厂模式”，三层类套下来别人得翻五个文件。直接创建一个对象就行——模式是止痛药不是维生素，没病别乱吃。

  4. 4. 23种模式分三类

    23 种模式按用途分三类：创建型（5 种，管“对象怎么生出来”）、结构型（7 种，管“怎么组装”）、行为型（11 种，管“怎么协作”）。找模式先想：卡在创建、组装，还是协作上，一下缩小范围。

    “根据配置创建不同支付方式”是创建问题→工厂方法；“好多对象要互相通知”是协作问题→观察者。

  5. 5. 观察者模式：一对多广播

    一对多依赖：一个对象状态变了，所有依赖它的自动收到通知。像公众号：你关注了号主，一发文所有粉丝自动收到推送，不用轮询“更新了吗”。

    股票 App：股价一变，所有打开这只股票页面的手机都要刷新。股价对象只管广播“我变了”，加 100 个新页面，股价对象一行不用改。

  6. 6. 策略模式：算法随便换

    把一堆“二选一、多选一”的算法封装成独立的类，互相替换。调用方只管“我要算”，不管“怎么算”。加新算法，加个类就行，不碰老代码。

    商城打折：普通 95 折、VIP 85 折、员工 7 折。不用策略就是一堆 if-else，加一种用户就得改核心代码。用策略，加“合作伙伴 8 折”新建一个类，老代码不动。

  7. 7. 工厂模式：把创建对象的事藏起来

    创建对象别让调用方直接动手，交给“工厂”管。调用方只说“我要个日志记录器”，工厂决定给控制台版还是文件版。“怎么创建”和“怎么使用”解耦，换实现不影响调用方。

    日志系统：开发环境打控制台，生产环境写文件。调用方找工厂要记录器，从开发切生产改个配置就行，业务代码一个字不动。

▼ 一、面向对象设计核心铁律 经典模式背后的底层公理与架构价值观

两大核心底层军规

所有模式共同尊奉的永恒基石

  • • 针对接口编程，而不是针对实现编程（Program to an interface, not an implementation）：客户只需了解抽象接口，彻底解耦具体实现类
  • • 优先使用对象组合，而不是类继承（Favor object composition over class inheritance）：继承破坏了封装性（白箱复用），组合保持了边界独立（黑箱复用）
  • • 封装变化点：找出应用中可能变化的部分，将其与不需要变化的部分分离开来

设计模式的分类体系

按照目的与范围划分的模式全景

  • • 目的维度：创建型（关注对象的创建）、结构型（关注类与对象的组合）、行为型（关注对象间的通信与职责分配）
  • • 范围维度：类模式（关注类与子类之间的静态关系，编译期确定）、对象模式（关注对象间的动态关联，运行期可变）
  • • 模式语言：为软件工程师提供了高密度、高精度的共同交流词汇
▼ 二、创建型模式（Creational Patterns） 抽象对象的实例化过程，解耦对象的创建与使用

工厂体系与单例

优雅解耦类实例化的核心技巧

  • • 工厂方法（Factory Method）：定义一个创建对象的接口，让子类决定实例化哪一个具体类
  • • 抽象工厂（Abstract Factory）：提供一个接口，创建一系列相关或相互依赖的对象家族，而无需指定具体类
  • • 单例模式（Singleton）：保证一个类仅有一个实例，并提供一个访问它的全局访问点（需注意线程安全与单测可 Mock 性）

建造者与原型模式

应对复杂构建与快速复制场景

  • • 建造者（Builder）：将一个复杂对象的构建过程与它的表示分离，使得同样的构建过程可以创建不同的表示
  • • 原型模式（Prototype）：用原型实例指定创建对象的种类，通过深浅拷贝这些原型来创建新的对象
▼ 三、结构型模式（Structural Patterns） 组合类与对象以形成更大、更灵活的复杂结构

适配器、装饰器与代理

接口转换、职责增强与访问拦截

  • • 适配器（Adapter）：将一个类的接口转换成客户希望的另外一个接口，解决接口不兼容问题
  • • 装饰器（Decorator）：动态地给一个对象添加额外的职责，比生成子类方式更为灵活，符合开闭原则
  • • 代理（Proxy）：为其他对象提供一种代理以控制对这个对象的访问（远程代理、虚拟懒加载代理、安全保护代理）

外观、组合、享元与桥接

树状组合、统一门面与细粒度共享

  • • 外观（Facade）：为子系统中的一组接口提供一个一致的高层门面，极大降低外部调用复杂度
  • • 组合（Composite）：将对象组合成树形结构以表示‘部分-整体’的层次结构，使用户对单个对象和组合对象的使用具有一致性
  • • 享元（Flyweight）：运用共享技术有效地支持大量细粒度对象的复用，极大节省内存开销
  • • 桥接（Bridge）：将抽象部分与它的实现部分分离，使它们都可以独立地变化
▼ 四、行为型模式（Behavioral Patterns） 算法分配与对象间责任协作的高阶艺术

解耦通信：观察者、策略与模板方法

发布订阅、算法替换与固定骨架

  • • 观察者（Observer）：定义对象间的一种一对多的依赖关系，当一个对象状态改变时，所有依赖者都得到通知并自动更新
  • • 策略（Strategy）：定义一系列算法，把它们一个个封装起来，并且使它们可相互替换，算法独立于使用它的客户
  • • 模板方法（Template Method）：定义一个操作中的算法骨架，而将一些步骤延迟到子类中，保持算法结构不变

状态与职责链：状态、责任链、命令

状态流转与请求接力处理

  • • 状态模式（State）：允许一个对象在其内部状态改变时改变它的行为，对象看起来似乎修改了它的类
  • • 责任链（Chain of Responsibility）：使多个对象都有机会处理请求，从而避免请求发送者和接收者之间的耦合关系
  • • 命令模式（Command）：将请求封装为一个对象，从而支持请求排队、日志记录以及撤销（Undo）操作

迭代与复杂计算：迭代器、访问者、备忘录

数据结构遍历与外置操作扩展

  • • 迭代器（Iterator）：提供一种方法顺序访问一个聚合对象中各个元素，而又不需暴露该对象的内部表示
  • • 访问者（Visitor）：表示一个作用于某对象结构中的各元素的操作，它使你可以在不改变各元素的类的前提下定义新操作
  • • 中介者（Mediator）与备忘录（Memento）：网状通信转星型解耦；捕捉并外化对象状态以便恢复快照

全书结构

  1. 第1章 引言

    确立设计模式核心定义（名称、问题、解决方案、效果），确立“针对接口编程”与“优先使用组合而非继承”两大面向对象设计基石。

    不直接将业务逻辑绑定在某个具体的 MySQL 连接类上，而是面向通用的 DatabaseConnection 接口编程，切换数据库无需改动上层业务。

  2. 第2章 实例研究：设计一个文档编辑器

    以文档编辑器 Lexi 为例，贯穿运用组合模式组织文档树、策略模式排版文本、装饰模式添加边框以及命令模式支持撤销重做。

    文字、图片和行容器统一实现 Glyph 接口（组合模式），排版算法单独抽象为 Compositor 策略，新增两端对齐算法完全无需触动文档结构。

  3. 第3章 创建型模式

    抽象工厂、工厂方法、单例、建造者与原型模式，将对象的实例化过程与客户端解耦，控制对象创建的灵活性。

    使用建造者模式（Builder）按步骤逐步装配包含几十个复杂网络配置项的 HttpClient，避免使用冗长且容易传错位置的重载构造函数。

  4. 第4章 结构型模式

    适配器、桥接、组合、装饰、外观、享元与代理模式，灵活组合类和对象以构建更大规模且低耦合的软件结构。

    使用适配器模式（Adapter）将旧系统的 XML 消息接口转换为新系统的 JSON 接口，老服务无需推倒重来即可接入全新中台。

  5. 第5章 行为模式

    职责链、命令、解释器、迭代器、中介者、备忘录、观察者、状态、策略、模板方法与访问者模式，分配职责与协调对象通信。

    利用状态模式（State）管理订单状态流转（待付款、已发货、已完成），每个状态封装自身的合法流转行为，消除庞大脆弱的 switch-case。

  6. 第6章 结论

    总结面向对象设计模式的认知图谱，警惕把模式当教条强行套用，拥抱简约原则，在演化中识别设计模式的真正时机。

    开发初期采用最简单清晰的直接实现，当业务发展出现多处变化与扩展痛点时，再针对性引入策略或工厂模式重构。
