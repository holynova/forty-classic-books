《架构整洁之道》

作者： 罗伯特·C·马丁
出版社： 电子工业出版社（博文视点）
出版年： 2018-9

好架构跟用什么框架、数据库没关系。关键是把“做什么生意”的代码和“用什么技术”的代码分开，让生意逻辑不被技术细节绑架。

总体观点

框架换了一茬又一茬，架构的好坏规则几十年没变过。这本书一次讲清这些不变的规则。

架构的终极目标：用最小的人力成本满足构建和维护系统的需求。软件有“行为价值”（能干活）和“架构价值”（好改），后者才是软件之所以“软”的原因。整洁架构用依赖规则把“做什么生意”和“用什么技术”彻底分开。

它给出了从编程范式、SOLID、组件原则到整洁架构的完整链条。六边形架构、洋葱架构、DDD分层，都是这套思想的不同讲法。

核心观点

  1. 1. 依赖规则：内圈的代码，永远不许知道外圈的存在

    全书最重要的铁律：依赖只能由外向内。内圈是业务规则（“买满200减20”），外圈是数据库、界面、框架。内圈定义接口、外圈实现，内圈绝不直接调用外圈的具体东西。换数据库、换框架，生意逻辑一行不用改。

    餐馆的核心是菜谱（内圈），用煤气还是电磁炉（外圈）不该影响它。菜谱里只写“加热”，不写“开煤气阀门”；换电磁炉，菜谱不用改一个字。

  2. 2. 同心圆：一个系统就四层，各就各位

    四个同心圆：最里实体（订单、折扣规则），往外是用例（下单、退款）。再往外是接口适配器（控制器、网关），最外是框架和驱动。越往里越稳定、越不常变。

    打车软件：实体是“行程”“计价规则”，用例是“下单”“接单”。适配器把App请求转成用例，最外层是MySQL、Spring。换库只动最外层，改计价只动实体。

  3. 3. SOLID：五个让代码好改的原则

    五个原则：单一职责（一个类只干一件事）、开闭（加功能靠扩展不改旧代码）、里氏替换（子类能顶替父类）。接口隔离（别逼实现用不上的接口）、依赖反转（依赖抽象不依赖具体）。全书都用这套尺子量代码。

    “订单类”既算价格又发短信还写库，改短信模板可能搞坏算价，拆成三个类各干各的。下单逻辑不调“支付宝SDK”而调“支付接口”，换渠道时下单逻辑不动。

  4. 4. 软件有两种价值：“能跑”和“好改”，后者更重要

    行为价值是“能干活”（下单成功），架构价值是“好改”（下周加新玩法不费劲）。老板只看得见前者，但“能跑改不动”的系统加个小功能要三周。架构师的天职是守护架构价值，让软件一直“软”下去。

    两个外卖系统都能下单：A加“拼团”要改20个文件、回归一周；B边界清晰，加个用例类两天上线。A团队每加一个功能慢一点，一年后基本不敢动代码——这就是架构价值被透支。

  5. 5. 编程范式不是给你“更多能力”，而是给你“立规矩”

    结构化拿走了goto（不许乱跳），面向对象拿走了函数指针乱指（必须走多态）。函数式拿走了可变变量（状态不能随便改）。每种范式都是少点自由、多份纪律，换来代码更好推理、更少怪bug。

    红绿灯限制了“随时走”的自由，换来路口不撞车。函数式不让变量随便改，“下单金额”定下来就没人能半路篡改，并发bug少一大半。限制让大规模协作成为可能。

  6. 6. 组件怎么分：聚什么、拆什么，都有讲究

    六条原则：三个管“哪些类放一起”（一起变的放一起），三个管“组件间怎么依赖”（依赖指向更稳定的方向）。别让底层牵着高层走。微服务拆成“分布式单体”，病根多半在这里。

    “用户中心”和“订单中心”拆成两个服务，改个手机号订单服务也得发版——该放一起的被拆开了。反过来，天天变的“短信发送”和稳定的“计价规则”绑一起，改短信总要重测计价。边界画错比不拆还难受。

  7. 7. 画出边界，把难做的决定往后推

    MySQL还是Mongo？Spring还是Django？都是“细节”。好架构让你晚做决定、随时反悔：业务核心和技术细节之间画边界、中间用接口隔开。业务代码只认接口，上线时再把具体实现“插”进来。

    “下单用例”只依赖“订单仓库接口”，先用MySQL顶着。用户量爆了，重写一个实现类插上去，用例代码一行不改。

  8. 8. 好架构的四个试金石：可测试、能并行开发、能独立部署、技术可换

    四个检验标准：业务逻辑能否脱离数据库界面单独测试；多团队能否各干各的不打架；组件能否单独上线；换框架数据库要不要伤筋动骨。全满足就是干净的，有一个不行就是边界没画对。

    装修：水电走完后换灯具品牌不该砸墙；木工油漆工能同时进场不打架；卫生间可单独验收。拿这四条一套，立刻知道架构合不合格。

▼ 一、软件架构的终极目标与双重价值 软件之所以称之为‘软’的根本原因

终极目标与人力成本曲线

架构好坏的唯一客观衡量标准

  • • 终极目标：用最小的人力成本来满足系统构建与维护的业务需求
  • • 代码行数与人员成本背离悲剧：不良架构导致随着代码量增加，新功能开发效率无限趋近于零，工程团队沦为修补救火队
  • • 唯有写好代码才能跑得快：‘先凑合上线后面再重构’是一句永远不会兑现的谎言

行为价值 vs 架构价值

艾森豪威尔紧急与重要象限的博弈

  • • 行为价值（Behavioral Value）：机器按照需求文档正确运行并赚钱（紧急但不总是重要）
  • • 架构价值（Architectural Value）：系统容易应对未来改变、易于演化（重要但不紧急）
  • • 架构师的不可推卸天职：坚决捍卫软件的‘可修改性’，抵制业务方将架构价值完全让位于短期行为价值的冲动
▼ 二、三大编程范式的约束本质 范式并不赋予新能力，而是剥夺危险能力

结构化、面向对象与函数式编程

近半个世纪软件工程的三大理论基石

  • • 结构化编程（Dijkstra）：剥夺 goto 语句，通过顺序、选择、循环三种控制结构实现代码的局部证明与分块递归分解
  • • 面向对象编程（OO）：通过多态机制实现‘控制反转’（IoC）；核心不是封装或继承，而是允许源码依赖方向跨越架构边界并反向于控制流
  • • 函数式编程（Functional）：剥夺赋值与可变变量（Immutability），消除多线程并发中的资源竞争、死锁与状态竞争问题
▼ 三、SOLID 面向对象设计原则 指导类与模块级设计的不变法门

单一职责与开闭原则（SRP & OCP）

应对变化与职责分离

  • • 单一职责原则（SRP）：任何一个模块应该只对某一类行为者（Actor）负责；不是‘一个函数只干一件事’，而是防止 CFO 的计算逻辑改动破坏 COO 的报表
  • • 开闭原则（OCP）：软件实体应当对扩展开放，对修改关闭；通过接口抽象与依赖反转，使新功能能通过添加新代码实现，而非修改已有代码

里氏替换、接口隔离与依赖反转（LSP, ISP, DIP）

子类兼容、接口契约与依赖倒置

  • • 里氏替换原则（LSP）：子类型必须能够替换掉它们的基类型而行为不破坏调用者；著名的‘正方形不是长方形’继承反模式
  • • 接口隔离原则（ISP）：不应强迫客户端依赖它们用不到的接口；胖接口必须拆分为细粒度的客户端专用接口
  • • 依赖反转原则（DIP）：高层业务策略模块绝不应依赖低层细节实现模块，二者都应依赖于抽象；抽象不应依赖细节，细节必须依赖抽象
▼ 四、组件构建原则（内聚与耦合） 指导 JAR / NPM / DLL 包与服务粒度划分

组件内聚性三大原则（REP, CCP, CRP）

决定哪些类应该打包放在一起

  • • 复用/发布等价原则（REP）：软件复用的最小粒度等同于其发布的最小粒度，必须有版本追踪与发布文档支持
  • • 共同闭包原则（CCP）：因为同样原因需要修改的类应该被组织在同一个组件中；这是 SRP 原则在组件级别的大尺度映射
  • • 共同复用原则（CRP）：不要强迫组件的用户依赖他们用不到的类；这是 ISP 原则在组件级别的对应物
  • • 内聚张力三角：REP/CCP/CRP 彼此制衡，项目早期偏重开发便利（CCP），成熟期偏重复用便利（REP/CRP）

组件耦合性三大原则（ADP, SDP, SAP）

管理组件间依赖关系与稳定性

  • • 无环依赖原则（ADP）：组件依赖关系图绝对不允许出现环；解除循环依赖可通过 DIP 引入新抽象接口或抽取公用组件
  • • 稳定依赖原则（SDP）：组件应该依赖于比自己更稳定的组件；稳定性指标 I = 传入依赖 / (传入依赖 + 传出依赖)，0为极稳定，1为极不稳定
  • • 稳定抽象原则（SAP）：组件的抽象程度（A）应该与其稳定性（I）成正比；极稳定的组件必须高度抽象，避免陷入‘痛苦区’（高稳定且高具象）
▼ 五、整洁架构（Clean Architecture）模型与边界划分 洋葱同心圆与独立于技术细节的纯粹业务内核

同心圆结构与依赖规则（Dependency Rule）

外圈是机制，内圈是策略

  • • 依赖规则：源代码依赖方向必须且只能指向同心圆内层；内层绝不允许出现任何外层的类、函数、变量或技术框架名称
  • • 实体层（Entities）：封装企业最核心的高阶业务规则与实体对象，不受任何外部应用场景变动影响
  • • 用例层（Use Cases）：封装特定应用的业务流程编排，接收输入、调用实体、产出结果，对具体 UI 和存储完全不知情
  • • 接口适配器层（Interface Adapters）：将用例与实体需要的数据格式转为外部技术所需的格式（Controllers, Gateways, Presenters）
  • • 框架与驱动层（Frameworks & Drivers）：最外层的易变细节，包括 Web 框架、数据库驱动、UI 控件、消息中间件等

边界划分与推迟关键决策

将所有框架和数据库视为可替换的插件

  • • 架构的插件化（Plugin Architecture）：让数据库、Web 服务器、消息总线都成为系统核心业务的插头（Plugin），随时可插拔替换
  • • 推迟决策（Deferring Decisions）：优秀架构师的标志是尽可能晚地做具体技术选型决策，在获得足够业务事实前保留最大的灵活性
  • • 测试作为架构的第一等公民：良好的架构天然具备高度可测试性（Testability），无需启动真实数据库和 Web 容器即可完成核心业务测试

全书结构

  1. 第1部分 概述

    软件架构的终极目标是最小化构建和维护系统所需的人力成本；易于修改的架构价值远高于当下能跑的行为价值。

    初版上线虽快但代码混乱，六个月后每加一个微小功能都需要十个人联调两周，人力成本呈指数爆炸式攀升。

  2. 第2部分 从基础构件开始：编程范式

    编程范式不是赋予更多能力而是施加限制：结构化限制 goto、面向对象通过多态反转限制函数指针、函数式限制可变状态。

    利用面向对象的多态性将业务核心与设备驱动解耦，替换硬件驱动只需实现标准接口，业务代码一行无需修改。

  3. 第3部分 设计原则

    SOLID 五大原则指导模块构建，单一职责（SRP）与依赖反转（DIP）为核心，使代码保持高弹性与低耦合。

    报表生成模块的高层策略只依赖报表格式抽象接口，具体的 PDF 导出或 Excel 导出作为实现细节注入，完全符合开闭原则（OCP）。

  4. 第4部分 组件构建原则

    指导代码包如何内聚（REP/CCP/CRP）与解耦，遵循无环依赖原则（ADP）、稳定依赖原则（SDP）与稳定抽象原则（SAP）。

    包与包之间决不允许循环依赖；不稳定的底层业务包必须单向依赖极其稳定的核心抽象包，保证核心不受外围摇摆冲击。

  5. 第5部分 软件架构

    整洁架构同心圆与依赖规则：代码依赖必须永远单向指向内圈高阶业务实体，用例主导架构，外围技术均属插件。

    核心业务实体在最内圈，外圈的 Web Controller 或命令行工具都只是调用内圈用例（UseCase）的简单外壳，随时可替换。

  6. 第6部分 实现细节

    数据库、Web 框架、UI 界面甚至外部通信都是可以推迟决定的外围实现细节，好架构必须清晰尖叫着表达其业务本身。

    系统架构的顶层目录一眼看去是订单、库存、借贷等业务概念（尖叫架构），而不是 Controller、View、DAO 等千篇一律的框架八股骨架。
