微服务“模式词典”：拆服务、服务间通信、分布式事务这些难题，一个个给出经过验证的解法。

总体观点

微服务正火，但缺一本“动手指南”。拆多细、服务间怎么通信、分布式事务怎么办，全是坑。Chris Richardson把这本书写成了微服务的“模式词典”。

微服务不是“把单体拆小”那么简单：拆完之后，通信、事务、查询、部署全是新问题。但前人都踩过，都可以沉淀成模式。书里用统一的“模式语言”（问题、方案、利弊）讲了几十个模式，每个决策都有章可循。

它让微服务从“玄学”变成“工程学”。选型不再靠拍脑袋：分布式事务的标准答案是Saga，协同和编排两种做法，利弊都列清楚。

核心观点

  1. 1. 先想清楚再拆：单体地狱和微服务地狱一样可怕

    单体做大变“单体地狱”：代码耦合、部署半小时、改一行提心吊胆。微服务拆不好变“微服务地狱”：分布式事务、网络延迟、运维爆炸。微服务不是银弹，团队小、业务简单时，单体可能是更好的选择。

    5个人、2万行代码拆成20个微服务：部署协调20个仓库，出问题查20份日志。新人三个月看不懂全貌——这就是微服务地狱。

  2. 2. 怎么拆服务：跟着业务拆，别跟着技术拆

    两套方法：按业务能力拆（电商天然有商品、订单、支付），或按子域拆（DDD的“限界上下文”）。核心一条：高内聚、低耦合，一个服务只干一类事，服务之间少废话。

    按“商品、订单、支付、库存”拆成四个服务，各有自己的库和团队。这就是限界上下文：一个服务管好一块业务，谁也别伸手到别人地盘。

  3. 3. 服务之间怎么说话：同步像打电话，异步像发微信

    两种说话方式：同步（REST、gRPC，像打电话，实时但互相等）和异步（消息队列，像发微信，解耦但有延迟）。

    查订单详情调订单服务，订单服务又调商品和用户服务——同步像套娃，一层慢层层慢，一个挂全挂。能异步就异步：下单成功发个“订单已创建”事件，库存、物流各自订阅处理，谁也不用等谁。

  4. 4. Saga模式：没有分布式事务，就用“分步提交+补偿”

    微服务处理分布式事务的标准答案：大事务拆成一串本地小事务。每步成功发事件触发下一步；哪步失败，反向执行补偿操作撤销前面。

    下单要做三件事：创建订单、扣库存、扣钱，三个服务三个库，没有传统事务。Saga：前两步成功、第三步扣钱失败，别慌，执行补偿——库存加回去、订单标失败。没有“要么全成功”，只有“失败了能撤销”。

  5. 5. CQRS：读写分开，查得快才重要

    命令查询职责分离：写和读用不同模型。微服务里数据散在各处，跨服务查又慢又复杂，干脆为查询单独建模、单独优化。代价是数据有短暂延迟（最终一致），换来查询性能大幅提升。

    CQRS建一个“查询服务”，平时订阅各服务事件把数据拼好存自己这。用户查详情只问它，一个请求搞定，又快又稳。

  6. 6. 事件溯源：不记余额，只记每一笔流水

    不直接存“当前状态”，存“导致状态变化的一串事件”。状态随时重放算出来，天然带审计日志，调试回滚都方便。代价是概念绕、查询要额外建模，适合审计追溯要求高的场景（金融、订单）。

    账户100元花了30：传统做法把余额改成70，事件溯源记一笔“支出30元”，余额是算出来的。想查账，把所有流水重放一遍就行，一笔都丢不了。

  7. 7. API网关：给前端一个统一的门面

    前端不该直接面对几十个微服务。API网关是统一门面：鉴权、限流、路由、拼装一站式搞定。BFF更进一步：给每种客户端定制专属接口，App要的和网页要的可以不一样。

    App只调一个API网关，网关在后面把20个调用拼好一次返回。还可以给App、网页、小程序各配专属网关，各取所需。

  8. 8. 绞杀者模式：别重写老系统，一点点“勒死”它

    全书压轴，也最实用：别想“推倒重写”，那是找死。在老系统外套一层新服务，新功能走新服务，老功能逐步迁移，流量一点点切。风险可控、随时回滚，是绝大多数团队落地微服务的真实路径。

    10年历史的老单体谁也不敢重写：新功能做成微服务挡在前面，流量一点点切过去。几年后老系统只剩空壳，自然退役——像绞杀榕缠死大树一样。

▼ 一、微服务架构模式语言与拆分策略 系统化模式语言指导架构决策

逃离单体地狱与模式语言体系

客观认知微服务的利弊权衡

  • • 单体地狱的症状：代码库极度膨胀、启动和测试缓慢、技术栈过时锁定、局部代码 Bug 导致整站宕机
  • • 微服务不是银弹：微服务架构带来了网络调用开销、分布式数据一致性、跨服务查询困难与测试运维高门槛
  • • 模式语言体系：全书将微服务解构为服务拆分、通信、数据管理、查询、部署、可观察性六大核心模式簇

业务边界拆分方法论

基于业务而非技术层切分系统

  • • 按业务能力分解（Decompose by Business Capability）：基于企业业务架构与核心能力树定义服务（如订单管理、库存管理、发票服务）
  • • 按 DDD 限界上下文分解（Decompose by Subdomain）：基于领域驱动设计的核心子域、通用子域与支撑子域划定服务界限
  • • 拆分阻力与对策：网络延迟（细粒度服务合并或批量 API）、分布式事务（采用 Saga 替代 2PC）、数据孤岛（通过事件驱动同步复制）
▼ 二、进程间通信与外部 API 模式 微服务网络调用的设计原则

同步通信 vs 异步消息通信

耦合度与可用性的权衡

  • • 同步 RPC（REST / gRPC）：简单易用但服务间时空紧耦合；调用链一旦过长可用性等于各服务可用性乘积，必须引入超时与断路器防雪崩
  • • 异步消息发布/订阅（Message Broker）：通过 Kafka/RabbitMQ 彻底解耦发送方与接收方，天然具备削峰填谷与缓冲能力
  • • 事务性发件箱模式（Transactional Outbox）：在本地数据库同一个事务中同时保存业务数据和待发送事件到 outbox 表，再由独立消息中继异步投递，绝对保证消息不丢失

API 网关与前端后置（BFF）模式

对外暴露统一而优雅的门面

  • • API 网关模式（API Gateway Pattern）：为所有外部客户端提供统一入口，负责路由分发、API 组合聚合、协议转换、安全认证与限流熔断
  • • 前端后置模式（Backends for Frontends, BFF）：针对 Web 端、移动 App、第三方合作伙伴分别定制专用网关，隔离不同客户端对数据结构的异构诉求
▼ 三、分布式事务治理：Saga 模式 彻底抛弃 2PC，拥抱最终一致性

Saga 模式的原理与运行机制

微服务分布式事务的标准解法

  • • 放弃两阶段提交（2PC）：2PC 存在协调者单点阻塞、严重拉长事务持有锁时间、违反微服务独立自治底线
  • • Saga 的核心定义：将一个分布式事务拆分为一系列由事件或消息串联的本地事务（Local Transactions）序列
  • • 补偿事务（Compensating Transactions）：某个本地事务执行失败时，Saga 必须按相反顺序依次执行各个前置事务的补偿操作回滚业务状态（如扣款失败时回滚库存占用）

协同式 vs 编排式 Saga

分布式事务的两种实现路线对比

  • • 协同式 Saga（Choreography）：去中心化，参与方监听领域事件并决定是否执行本地事务及发布新事件；逻辑简单但缺乏全局全景，容易陷入事件网循环依赖
  • • 编排式 Saga（Orchestration）：设立中央 Saga 编排器（Orchestrator），由状态机向各微服务发送命令消息并接收响应；逻辑集中明确、易于排查和测试，复杂业务首选
▼ 四、微服务数据查询：CQRS 与事件溯源 跨服务复杂聚合查询与数据可靠落盘

命令查询职责分离（CQRS 模式）

解除分布式 JOIN 查询难题

  • • 跨服务查询痛点：微服务数据库私有后，无法直接执行跨库 SQL JOIN，API 组合模式（API Composition）在海量数据下内存开销与网络往返不可承受
  • • CQRS 核心思想：将系统拆分为命令侧（Command / 写模型）与查询侧（Query / 读模型）；写模型专注业务校验与事务，通过事件将变更同步给只读视图库（如 Elasticsearch/MongoDB）实现极致查询性能

事件溯源（Event Sourcing）

以事件作为唯一事实来源的持久化技术

  • • 不存最终状态，只存不可变事件序列：数据库中不再保存账户余额字段，而是持久化每一笔‘充值’、‘消费’事件追加记录（Event Log）
  • • 巨大优势：具备 100% 完整的历史审计轨迹、支持任意时间点重放重建状态、天然消灭对象-关系阻抗失衡
  • • 快照机制（Snapshotting）：定期为实体生成状态快照，避免重放数万个事件导致的性能迟钝
▼ 五、测试与单体重构迁移策略 从单体安全平滑过渡到微服务

绞杀者模式（Strangler Fig Pattern）推进重构

微服务改造的稳健路线图

  • • 绝对禁止推倒重来：大爆炸式全量重写几乎 100% 会导致项目延期超支甚至团队解体
  • • 渐进式替换三步走：先在新功能上使用微服务（保持新业务纯净）、通过 API 网关拦截旧流量逐步转发至新服务、最后将遗留单体彻底架空废弃

全书结构

  1. 第1章 逃离单体地狱

    单体系统在团队与代码膨胀后必然陷入交付迟缓、部署恐惧的单体地狱；微服务通过模块化与数据库私有化恢复研发敏捷。

    FTGO 餐饮配送单体系统代码库过大导致本地启动需20分钟，一次微小改动需全公司协调测试两周，拆分微服务成为重获新生的唯一出路。

  2. 第2章 服务的拆分策略

    依据业务能力或领域驱动设计（DDD）的子域拆分服务边界，确保每个服务松耦合且高度内聚，遵循单一职责。

    按照订餐、送餐、餐厅管理与计费四大业务子域划分出对应的独立微服务，每个服务由一个专注的专属小组全权负责。

  3. 第3章 微服务架构中的进程间通信

    同步 REST/gRPC 与异步消息队列（Message Broker）通信模式的选型与权衡，利用事务性发件箱（Transactional Outbox）确保消息不丢。

    更新本地数据库与发送消息在同一个本地数据库事务中先写入 `outbox` 表，再由独立轮询或 CDC 进程将消息可靠推至 Kafka 队列。

  4. 第4章 使用Saga管理事务

    在没有分布式 2PC 强一致事务的环境中，运用 Saga 模式通过协同式（Choreography）或编排式（Orchestration）的本地小事务加补偿事务保证最终一致。

    用户下单时 Saga 编排器依次调用订单、客户额度与餐厅服务；当餐厅拒绝接单时，编排器自动反向调用补偿事务撤销客户冻结额度并关闭订单。

  5. 第5章 微服务架构中的业务逻辑设计

    结合 DDD 聚合（Aggregate）模式组织业务逻辑，聚合边界即 ACID 事务边界，状态变更后发布领域事件驱动外部协作。

    Order 聚合根在内部校验修改商品明细并保证总价正确，状态变更后发布 OrderRevised 事件，其他服务通过事件订阅完成联动。

  6. 第6章 使用事件溯源开发业务逻辑

    以不可变的领域事件序列作为状态真实持久化的唯一事实源，消除对象-关系阻抗失配，天然具备完备审计日志与时间旅行回溯能力。

    不直接将银行账户余额覆盖更新为 70 元，而是顺序追加存储一条 `MoneyDebited(30)` 事件，当前余额通过按序重放事件流累加求出。

  7. 第7章 在微服务架构中实现查询

    使用命令查询职责分离（CQRS）为跨服务数据视图单独建模与维护只读副本，彻底解决微服务各持数据库后无法跨库关联查询的痛点。

    订单历史查询服务订阅来自订单、餐馆和配送服务的事件流，在本地 Elasticsearch 中维护宽表只读视图，用户查询历史订单仅需单次极速检索。

  8. 第8章 外部API模式

    引入 API 网关与 BFF（Backend For Frontend）模式，为移动 App、网页等不同终端提供统一入口、路由协议转换与数据聚合。

    手机客户端发起一次网络请求，API 网关在内网并发调用商品、促销与用户服务并将结果拼装成适配手机屏幕的 DTO 一并返回。

  9. 第9章 微服务架构中的测试策略（上）

    坚守测试金字塔基础，深入实施针对实体与领域服务的细粒度单元测试，运用桩（Stub）与模拟（Mock）隔离外部基础设施依赖。

    为订单聚合根编写密集的单元测试验证各种边界折扣计算，完全无需启动真实的 Spring 容器或连接真实的数据库，毫秒级执行完毕。

  10. 第10章 微服务架构中的测试策略（下）

    采用消费者驱动契约测试（CDC）与组件测试（Component Test），替代成本高昂、执行极慢且脆弱易崩的大爆炸端到端集成测试。

    订单服务利用 Spring Cloud Contract 模拟下游计费服务并进行契约断言，在单服务隔离环境下快速完成接近真实的集成行为验证。

  11. 第11章 开发面向生产环境的微服务应用

    构建生产就绪能力：安全认证、外部化配置中心、健康检查端点、Prometheus 指标埋点、集中式审计日志与分布式分布式链路追踪。

    服务启动时自动从 Consul/Nacos 动态拉取环境配置，并通过 Micrometer 暴露连接池利用率与 P99 延迟指标给 Prometheus 实时抓取监控。

  12. 第12章 部署微服务应用

    全面评估虚拟机、Docker 容器、Kubernetes 编排以及 Serverless 部署模式的成本效益，推行基于服务网格（Service Mesh）的现代化运维。

    使用 Kubernetes Deployment 管理微服务容器的副本数与滚动更新，并通过 Istio 边车代理（Sidecar）透明实现金丝雀灰度引流与跨服务 mTLS 加密。

  13. 第13章 微服务架构的重构策略

    采用绞杀者模式（Strangler Pattern）逐步将单体功能迁移至微服务，严禁推倒重来，通过胶水层（防腐层）打通新旧系统平滑过渡。

    在老单体前面架设路由反向代理，优先把送餐管理模块实现为全新微服务并把对应 URL 流量切过来，老单体逐步被蚕食镂空直至安全下线。
